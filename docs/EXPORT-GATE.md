# Export policy choices for Site Studio 0.1.5

The current implementation requires dashboard-session authorization and explicit confirmation. The agent-export path below is a proposed design: it is not implemented and not supported, and this document does not change that boundary.

## Verified current boundary

- `src/options.js`, `options` accepts a startup export destination through `--export-dir`. This selects a folder, not agent authority. Without that destination, `src/web-publisher.js`, `exportSite` refuses with “No export destination configured.”
- `mcp-web.js`, `call` validates the registered tool set; export is absent. Its initialization instructions say “Never obtain, print or use the human launch link secret.” `web_preview` returns clean origins without the dashboard capability.
- `src/web-server.js`, `hasSession` requires the consumed launch secret's dashboard token in `x-site-studio-control`. `/api/control` also checks the loopback Host, exact Origin and JSON content. Preview cookies cannot authorize it. The one-time `/api/session` exchange refuses replay.
- `public/web-app.js`, `confirm-export` sends `confirmed:true` with the revision displayed by the confirmation dialog. `src/studio-store.js`, `human` refuses a stale revision and any export without `confirmed === true`.
- `src/web-publisher.js`, `exportSite` checks destination separation, source drift and an exclusive destination lease. A new destination leaves the source intact; replacing the original retains its previous folder as a backup. Export does not deploy or publish remotely. Ordinary promotion/persistence failures roll back. A process or machine crash between the two directory renames can leave the original at its retained backup path, requiring manual recovery; retain the backup and independent copies of valuable sites.
- `src/studio-store.js`, `record` currently attributes confirmed exports to `human`. Any HTTP client holding the dashboard capability can confirm export if it supplies the required Host, Origin, JSON, current revision and confirmation fields. The server cannot distinguish an agent from a human capability-holder. The current `human` history entry is not an audit of agent authorization; the unsupported bridge is not an audited agent-export mechanism. `SECURITY.md` says “A process running as the same user can still act as the user”. A local agent with separate shell, file or browser access can cross the MCP boundary. Startup-log secrecy and host-tool restrictions therefore matter.

The reported website-build bridge read the one-time dashboard secret from stderr and confirmed exports. That pattern is **unsupported** under the current policy. This lane did not inspect or rerun that historical bridge; its use comes from the release brief. No secret value is reproduced here. Synthetic test fixtures redeem their own process-local secrets solely to verify the controls; that does not establish a supported agent workflow.

## Choice A — retain human confirmation

Prepared policy text, matching current behavior:

> Site Studio keeps export outside MCP. The human opens the private dashboard link before assigning agent work, reviews the destination and current revision, and confirms export there. Configuring an export destination does not grant an agent permission to export. An agent bridge that reads dashboard secrets from stderr or host logs and confirms exports is unsupported. Restrict the host's other tools when stronger separation is needed; these controls do not identify a physical human against same-user processes. A client holding the dashboard capability can act as that user; Site Studio cannot distinguish an agent from a human capability-holder. Replacing the original retains its previous folder as a backup. Ordinary promotion/persistence failures roll back, but a process or machine crash between folder renames can leave the original at the backup path. Keep that backup for manual recovery and independent copies of valuable sites.

Adoption keeps the existing runtime. The README now states the bridge limitation while the owner chooses. No new export flag or token is documented as supported.

## Choice B — explicit human opt-in and audited agent export

**Proposed design, not implemented or supported in 0.1.5.** There is no assigned flag name, token syntax, configuration key or MCP tool name for this proposal. Do not turn the design into invocation instructions before implementation, review and owner approval.

Prepared future policy text, conditional on that work:

> If the human explicitly enables agent export for a reviewed destination, Site Studio would permit only the authorized site revision under a separate, bounded grant and record the agent action and its human authorization in the receipt. Without that opt-in, export would remain human-confirmed in the dashboard. Dashboard-secret scraping would remain unsupported. Original replacement would retain the previous folder as a backup, preserving ordinary failure rollback and the existing crash boundary: a process or machine crash between folder renames can leave the original at that backup path and require manual recovery. Keep that backup and independent copies of valuable sites. A local capability or audit would not authenticate a physical human against a same-user process.

Requirements for a future implementation:

1. **Human authorization first.** Default disabled. The human intentionally enables the separate path through a documented startup/configuration or authenticated dashboard choice. Merely setting the destination, enabling external preview resources or exposing a launch log must not grant it. The UI must state whether the grant allows replacing the original, with the resulting backup and crash-recovery limits.
2. **Separate, narrow authority.** Do not reuse the launch secret, dashboard session token or preview cookie. Bind the grant to the current site/state identity, canonical startup destination, reviewed revision and content digest, permitted operation and an expiry. Prefer a single export; any broader count needs explicit human authorization. Deny request-supplied destination changes and unknown fields. Deliver any capability through an intentional private human handoff, never dashboard-log scraping or ordinary read-tool results.
3. **Visible revocation.** Display granted scope and remaining use; let the human revoke it. Refuse expired, revoked, replayed, wrong-site, wrong-destination or stale-revision requests. Restart must not silently restore a grant. Pause should suspend agent export unless the human explicitly authorizes another documented policy. Keep dashboard-session renewal and agent-grant revocation behavior explicit.
4. **Reuse export safety.** Keep source-drift, path-separation, private-file, destination-existence and exclusive-lease checks. Keep the backup and ordinary failure rollback when replacing the original. Never treat the existing advisory preflight as authorization. No network deployment is implied.
5. **Honest audit and receipt.** Record the actor as `agent`, the human grant's nonsecret identifier, bound destination/site, approved revision/digest, grant/attempt/outcome timestamps and backup reference. Never label an automated action `human`. Keep secret values out of histories, errors, tool results and logs. Persist authorization evidence before export and the outcome with the existing rollback/durability semantics; audit failure must not become a silently unaudited success. Define concurrent attempts and crash recovery before implementation. This local audit is not tamper-proof against the same OS user.
6. **Independent review before support.** Review the new authority surface and delivery channel. Verify the source and extracted artifact. Update README, SECURITY and protocol docs together only after the owner chooses and the implementation meets the behavior checks below.

Future acceptance checks, **specified but not run**: absent opt-in refuses without destination writes; a valid single-use grant exports exactly the reviewed bytes; destination/site/revision/digest changes refuse; expiry/revocation/restart/replay refuse; preview/dashboard credentials cannot stand in for the grant; unknown fields refuse; parallel attempts cannot exceed the authorized count; source drift and existing unrelated destinations refuse; original replacement retains the backup; persistence failure rolls back; pause behavior matches its documented policy; receipts identify `agent` and its human authorization without credentials. Targeted mutations must produce RED, followed by restored GREEN, before these checks become release gates.

## Decision and verification status

Both choices are prepared. Choice B is not a release feature, and this document does not authorize implementing it. Current policy remains in effect pending the owner's decision. The documentation worker's exact behavioral checks, mutation outputs, bounds and unknowns are recorded in the lane's `.fleet/reports/docs-final.md`; they do not claim native Windows/macOS qualification or final-archive acceptance.
